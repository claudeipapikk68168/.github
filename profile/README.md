<p>评测静态住宅 IP，最容易犯的错是拿一个场景的结果去概括全部。登录顺不代表订阅能过，订阅能过也不代表 API 调用不掉线，因为三者触发的检查项完全不同。这篇给一套可复制的对照方法：同一账号、三条候选线路、三个场景，跑 12 天，把数据记成三张表。下面的数值来自一次小样本演示，样本有限，只用来示范怎么读，不代表任何服务商的普遍水平。</p>

<h2>一、实验设计：一个账号、三条线路、三个场景</h2>
<p>变量控制是这套方法的核心。账号只用一个，资料、订阅状态、设备、浏览器配置文件全程不变；唯一变化的量是出口线路。三条线路分别是：A 机房静态（美国西部）、B 静态住宅（同城 ISP 段）、C 静态住宅（邻城不同 ISP）。三条线都走同一台本地机器、同一个指纹浏览器配置文件，避免环境差异污染结果。</p>
<p>每个场景每天在三个固定时段各跑一次：当地 10:00、20:00、01:00。每次记录状态码、首字节、总耗时、是否出现验证。12 天下来，每条线每个场景各有 36 个样本。样本量不大，但足够看出量级差异。</p>
<h3>记录表怎么设计</h3>
<p>一行一次访问，字段固定为：日期、时段、线路、场景、状态码、首字节 ms、总耗时 ms、验证类型（无/图片/短信）、备注。用 CSV 存，后面好聚合。别用笔记软件随手记，格式一乱就没法比。</p>

<h2>二、登录场景：首屏时间与挑战页触发次数</h2>
<p>登录场景测两个东西：页面多久能交互，以及会不会被要求额外验证。前者用 curl 的 time_starttransfer 近似，后者靠人工记录。三条线的对比如下，数值为演示样本的中位数。</p>
<table><thead><tr><th>线路</th><th>首字节中位（ms）</th><th>登录页完全加载（s）</th><th>12 天验证次数</th><th>会话中断次数</th></tr></thead><tbody><tr><td>A 机房静态</td><td>210</td><td>2.4</td><td>7</td><td>2</td></tr><tr><td>B 静态住宅同城</td><td>265</td><td>2.9</td><td>1</td><td>1</td></tr><tr><td>C 静态住宅邻城</td><td>340</td><td>3.6</td><td>3</td><td>2</td></tr></tbody></table>
<p>结果很有意思：机房线的首字节最快，但验证次数最多；B 线慢了一点，验证次数却降到 1 次。这说明登录环节的体验瓶颈不在速度，而在出口画像。C 线两头都不占优，验证次数也高于 B，说明「同城」这个条件确实影响一致性。</p>
<h3>把验证次数换算成时间成本</h3>
<p>一次图片验证平均花 25 秒，短信验证要等 40 秒以上。A 线 12 天 7 次，折合约 3 分钟；B 线 1 次，约 25 秒。单看时间差不大，但验证频繁往往伴随会话变短，长任务被打断的损失远大于验证本身。</p>

<h2>三、订阅场景：支付页加载与出口一致性</h2>
<p>订阅环节的变量更多，风险也最高，所以这条不能靠反复试。做法是：只在需要续费时跑一次，记录支付页加载时间、是否出现地区提示、扣款是否一次成功。12 天里每条线各触发一次续费，样本只有 1，结论只能当参考。</p>
<p>更值得关注的是「出口一致性」这个前置条件。支付页加载期间如果代理抖动导致出口切换，即使最终扣款成功，也可能在账务侧留下不一致记录。所以测这条时要同时开一个每 10 秒一次的出口 IP 探测，记录整个支付过程中出口有没有变。</p>
<h3>一致性探测怎么做</h3>
<p>开一个终端跑 while 循环，每 10 秒 curl 一次 ipinfo.io/ip，把结果追加到文件；支付结束后统计不同 IP 的个数。个数为 1 才算全程一致。这个动作很土，但能抓到 90% 的隐蔽切换。</p>

<h2>四、API 场景：首字节、超时率和重试次数</h2>
<p>API 场景可以自动化，样本也最容易做多。写一个小脚本，每 10 分钟发一次最小请求（比如一次很短的对话补全），记录 HTTP 状态、首字节、总耗时，超时设为 30 秒，失败重试 1 次并记录重试结果。12 天每条线约 1700 次请求。</p>
<table><thead><tr><th>线路</th><th>成功率</th><th>首字节 p50 / p95</th><th>超时率</th><th>平均重试次数</th></tr></thead><tbody><tr><td>A 机房静态</td><td>99.4%</td><td>0.62s / 1.4s</td><td>0.3%</td><td>1.02</td></tr><tr><td>B 静态住宅同城</td><td>99.1%</td><td>0.78s / 2.1s</td><td>0.6%</td><td>1.05</td></tr><tr><td>C 静态住宅邻城</td><td>97.8%</td><td>0.95s / 3.8s</td><td>1.7%</td><td>1.19</td></tr></tbody></table>
<p>API 场景里机房反而更稳，这符合预期：长连接、低抖动是机房的强项。但注意 p95 的差距比 p50 大得多，B 线 p50 只慢 160 毫秒，p95 慢了 700 毫秒，说明住宅线路的尾部延迟更难看，晚高峰尤其明显。</p>
<h3>按小时拆开看尾部</h3>
<p>把 1700 条按小时聚合，单独看当地 20:00–23:00 的 p95。B 线在这三小时会从 2.1s 涨到 3.2s 左右，A 线基本不变。如果你的业务集中在这个时段，这个差异必须计入选型。</p>

<h2>五、三组数据合起来怎么看</h2>
<p>三条线各有胜负，没有全能冠军。判断方式是给三个场景分配权重，再乘各自得分。权重取决于你的实际用法：如果七成时间在做对话和订阅管理，登录与支付的权重就该高；如果主要在跑批处理，API 的权重高。</p>
<p>还有一个结论值得单独说：B 线在三个场景里都没有明显短板，虽然每项都不是第一。这种「均衡型」往往比「单项冠军」更适合长期账号，因为长期账号最怕的是某个环节突然掉链子，而不是平均慢 200 毫秒。</p>
<p>最后提醒，实验只能证伪不能证明。12 天数据说明某条线在你的场景、你的时段、你的账号上表现如何，换一个账号或换一个季度，结论可能变。所以这套方法的价值是「能重复」，不是「一次定终身」。</p>

<h2>常见问答</h2>
<h3>没有条件做 12 天对照，最短要跑多久？</h3>
<p>答：至少 3 天，且必须覆盖一个晚高峰和一个凌晨时段。3 天能看出量级差异，看不出周期性问题，所以结论只能用于初筛。</p>
<h3>样本量多少才有说服力？</h3>
<p>答：API 场景几百次就够看趋势，登录和订阅场景因为触发次数少，只能靠时间累积。这两项建议记录至少两周，并把每次异常的截图一起留档。</p>
<h3>为什么机房线在 API 场景反而更好？</h3>
<p>答：机房靠近骨干网，路由跳数少、抖动小，长连接更稳。住宅线路的城域网段共享度高，尾部延迟容易拉长，这在 p95 上体现得最明显。</p>
<h3>三条线结果打平，怎么定？</h3>
<p>答：比售后和替换政策。技术指标接近时，能在两小时内响应、每月给免费替换的那家，长期成本更低。</p>
